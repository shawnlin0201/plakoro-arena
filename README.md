# PLAKORO ARENA
遊玩網址：https://shawnlin0201.github.io/plakoro-arena/dist/
支援版本：預組 01-09，探險隊 01。（共 15 隻寶可夢、126 個招式）

# 目前功能主要包含了
- 雙人對戰：基本上與 PLAKORO 原先規則相同，主要是用來輔助玩家對戰遊玩
- 單人爬塔：享受基於 PLAKORO 規則所改編的 Rougelike 遊戲，至少需要一組預組才能遊玩
- 模擬組骰：離線試組能量骰，可 3D 擲骰、比較兩組骰子、查看能量組合機率與各招式成功率
- 店家資訊：查看店家地圖、賽事行事曆與店家清單

# 單人爬塔
> 『踏上 PLAKORO 的冠軍之路！』你將在旅途中遇到其他訓練家，從戰鬥中逐步累積經驗並強化 PLAKORO 的能力，打敗三大天王贏得 PLAKORO 冠軍！

## 與 PLAKORO 不同的是
- 初始狀態只擁有一顆能量骰子與兩樣招式
- 招式學習耗能不超過當下骰子數量 * 2
- 電腦執行招式：替電腦丟角色骰+關卡數量的骰子（ex: 第一關只丟一個），並只看能量數量不看能量顏色。

## 在戰鬥過程中你可能會遇到
- 戰鬥：與其他電腦訓練家對戰並獲得經驗值。
- 事件：各種與寶可夢相遇的事件，有機會強化你的 PLAKORO
- 篝火：回血回血！休息是為了走更長遠的路。

## PLAKORO 成長方式
戰鬥：過程中累積經驗值後可以從攻擊/防禦/HP 上限擇一增加
打敗天王：獲得新的招式

## 無法出招時
爬塔起手只有兩招，可能遇到「一招被對手封印、另一招是上回合剛用過」而無招可出的情況（招式滿四招時不會發生）。此時招式面板會出現「跳過這回合」按鈕，跳過後下一回合即恢復可用。電腦遇到相同狀況時也會跳過該回合。

# 模擬組骰
> 離線試組屬於自己的能量骰，測試不同搭配下的擲骰結果與機率分布。

## 能量骰構造
一顆完整能量骰由兩個半顆組成：
- 2 面固定類型（無法更改）：凸面固定為草/火/水/雷/鋼其中一種，凹面固定為惡/鬥/超/飛其中一種
- 2 個圓槽：插單能量晶片（任意一種類型）
- 2 個方形槽：插雙能量晶片（可選兩種類型，斜線分半，也可以相同）

## 組骰功能
- 點擊任一面即可開啟能量選擇視窗調整該面能量
- 骰子2、骰子3可勾選「與骰1相同」，之後骰子1的任何調整都會即時同步過去
- 快速套用純屬骰：先選**主能量**，圓槽、方槽全部換成它，同一個屬性池的固定面（凸面或凹面）也一起換；再選**副能量**指定另一面 —— 凸面只能是草/火/水/雷/鋼、凹面只能是惡/鬥/超/飛，一種能量填不滿兩面，所以分兩步選。副能量可以跳過，那一面就維持原樣
- 每顆骰子名稱下方也有一顆「純屬骰」按鈕，只套用到那一顆。對已勾「與骰1相同」的骰子按下去會自動解除同步，否則下次調整骰1時這次的設定會被蓋掉
- 新增一組骰子來比較：可再開一組「骰組 B」（建立時複製骰組 A），之後機率表與招式機率都會並列顯示兩組數字，用來比較「改一個面差多少」

## 模擬擲骰
- 3D 擲骰：真實物理模擬（Three.js + cannon-es）的擲骰台，按住畫面聚攏骰子、拖曳搖晃、放開擲出，由骰子實際落地的面決定結果
- 快速擲骰：略過動畫直接取得結果

## 結果機率表
整理三顆骰子一起擲的 216 種面組合，依「最終集齊的能量組合」統計機率並降序排列。
- 只看：複選特定能量來篩選組合
- 依數量排序：把相同能量數量的組合分組彙總（可收合展開查看細項）
- 顯示累計機率／顯示恰好機率：在分組模式下切換。「恰好 N 個」是剛好擲出該數量的機率，「N 個以上」是累計機率（例如招式需要 3 個火，能付得起的是「3 個以上」而不只是剛好 3 個）
- 顯示次數：勾選後除了百分比也顯示 `n/216` 的次數

## 招式機率
選一隻寶可夢，列出牠**所有**招式在目前骰子配置下的成功率（能湊出招式所需能量的機率）。
- 「無色」需求可由任何能量支付，其他屬性則必須由該屬性支付
- 參與擲骰：可個別設定每顆骰要擲幾次（有些規則允許同一顆骰擲多次），機率會依總擲骰次數重算
- 角色骰效果標示於卡片下方，顯示的是**累進機率** —— 招式要先成功才會進行角色骰判定，所以是兩者的聯合機率（例如招式 80%、角色骰 3/6，實際發動為 40%）
- 有骰組 B 時，每個招式都會並列顯示兩組的機率

### 期望效益
成功率只說得出「打不打得出來」，期望效益進一步回答「划不划算」。每個招式在成功率下方顯示一個數字，代表這一招平均換來多少 HP 差距：

`期望效益 = 成功率 ×（對手扣血 − 自己扣血）的平均`

- 數字下方列出這個期望效益的組成，**相加剛好等於上面那個數字**（`傷害總共` 除外，它是小計，見下）：`白板`（卡面印的傷害）＋`角色骰`（角色骰判定平均多打的傷害）－`自身 HP`（自傷；回血則為正）＋`減傷`（只在有勾折算時出現）
- 招式如果也會扣自己的血，`角色骰` 後面會多出一個 `傷害總共` —— 那是 `白板 ＋ 角色骰` 的**小計**，讓「這一招到底打出去多少」不用自己在腦中相加。它是小計不是加項，**別再跟前兩項一起加**：`傷害總共 ＋ 減傷 － 自身 HP` 才等於上面那個數字。只有在角色骰真的分到傷害、而且後面還接著非傷害項目時才顯示 —— 角色骰沒分到傷害時它只是重複 `白板`，後面沒有東西時它只是行末又一個看得出來的數字
- 回血在資料裡就是負的自傷（如「はねやすめ」的 -20），所以回血自動算成加分
- 「角色骰」那一份包含因為角色骰而多打的整輪（如「エレキラッシュ」重複整招所賺到的傷害），因為那些傷害本來就是骰出來的
- 角色骰的各組朝向互斥，因此依 `朝向數 / 6` 加權平均；擲多次的（「ダブルサンダー」）、失敗前可重擲的（「サンダーチェイン」）、讓對手擲的（「ファントムトリック」）都各自照規則展開計算
- **不計弱點加成**：這裡沒有指定對手，而弱點對「同一隻寶可夢的招式互相比較」不影響排序
- 「計算前提」面板可設定：依期望效益排序、剩餘 HP（影響「殘り HP 40 以下」類招式）、對手上一招的白板傷害（給「リフレクション」抄用）、上回合的前提條件、減傷折算為回血、干擾對手折算成傷害。**全部預設開啟、HP 與對手傷害預設 40** —— 想看素傷自己關掉即可
- 干擾折算：把「扣對手骰子／封角色骰／免傷／封招」等不直接影響 HP 的效果，換算成 HP 計價。算法是「對手正常能打出的最佳期望效益 − 被限制後能打出的最佳期望效益」，對手假設帶著適合自己角色的純屬骰、且會改選當下最划算的招。細節見 `src/game/tempoValue.js`
- 數字下方的 `＊` 只講計算本身的假設（需要填 HP、依前提條件、假設對手骰組、有未支援的效果）。卡面看得到的事一律不重複標註 —— 不影響 HP 的效果（增減骰、封招）算 0、抄對手招式或完全免傷算不出來，這些卡面本來就寫著了

計算邏輯在 `src/game/moveExpectedValue.js`，效果語意對應 `src/game/effectQueue.js`；遇到沒有對應處理的效果型別會直接標示「有未支援的效果」，而不是靜靜當成 0。

# 角色強度排行
每隻寶可夢都套用「自己招式最常要求的屬性」組成的 3 顆純屬骰，由高到低排序並附長條圖。點一列可展開背後的招式。

## 為什麼是「兩招輪替」而不是「最強招」
上回合用過的招會被鎖住（`MovesGrid.vue` 直接 disable `committedLastMoveId`），所以沒有人能一直出同一招 —— 穩態是**最強兩招輪替**。因此算的是前兩招的平均，不是單一最強招。

這不是小差別：用單一最強招去算，「平均一回合」會退化成「誰的最強招期望效益高」，實測ファイヤー／ミュウ／ゲンガー 會算出一模一樣的 34.7，因為那字面上就是同一個數字重複三次。

選 3 招是給「被對手用『相手のワザを１つ選ぶ』封掉一招」的情況參考。

## 兩種算法可切換
- **最強 N 招平均**：問「這隻的招牌招輪替起來有多強」
- **平均一回合**：再疊上血量區間（>80 佔 50%、80 以下 25%、40 以下 25%），每段取「那時候打得出的最強 N 招輪替」再加權

兩者只在**有低血條件招的角色**上會不同（15 隻裡 4 隻），其餘完全一致 —— 這是對的，它們本來就只該在條件咬合的地方分歧。

## 條件式招式怎麼算
有 8 招要滿足條件才有強度。全部算成不成立會低估，全部算成成立則是賴皮（ルカリオ 有三招吃低血，會直接衝上榜首）。分野在**誰決定條件**：

- **自己湊得到的**（「上回合どくガス成功的話」）→ 連同湊條件那一回合一起算成序列平均。這不是為了公平而加的懲罰，而是那組序列真實的價值：どくガス 成功率 100% 但本身只值 13.5，兩回合平均 24.8，**輸給直接用ベトベトなげ打兩次的 28.6**，所以臭泥其實沒有變強
- **自己選不到的**（剩餘血量、上回合骰失敗）→ 依實際發生頻率加權。頻率從卡池推導：平均 120 HP ÷ 每回合 30.6 傷 ≈ 4 回合 → 血量 40 以下佔 25%、80 以下佔 50%；上回合骰失敗 = 1 − 玩家實選招式平均成功率 0.84 = 16%

有第三種寫法「只在條件達成時才出，否則出別招」看起來最直覺，但它是錯的：那會把別招的分數記在這一招頭上（カイロス「ぎゃくじょうスイング」會算出 27.4，比它條件達成時的 24.0 還高），等於每個有條件招的角色都把最強招重複計分。那衡量的是「一回合值多少」——那是「平均一回合」那個算法的工作。

## 其他
- 長條**從 0 起算**，不是從最低分起算。實際落差是最高分的 75%～100%，從最低分起算會把這個溫和的差距畫成鴻溝
- 非傷害效益（減傷、干擾）預設折算。這是這張表最有價值的地方：像「10まんボルト」帳面 30 傷很猛，但它讓自己下回合少擲兩顆骰，折算後期望效益從 36 掉到 28，皮卡丘的排名也跟著往下
- 一樣不計弱點、不指定對手

# 店家資訊
- 地圖：可遊玩／販售店家的 Google 我的地圖
- 行事曆：賽事與活動行程
- 店家清單：從 Google 試算表讀取，可依「類型」標籤複選篩選（多選為 AND 條件）

# 開發
```bash
npm install
npm run dev          # 開發伺服器
npm run build        # 建置到 dist/
npm run fetch-data   # 從 Supabase 重新抓取角色與招式資料到 src/data/generated/
```

多語系（日／英／繁中）：介面文字在 `src/i18n/locales/`，寶可夢與招式名稱的翻譯在 `src/data/translations/`（以日文為基底，缺少翻譯時自動顯示日文原文）。

資料庫的部分欄位含有多餘空白（例如招式 `STW05-002` 的 id 尾端有換行字元），且無權限在 Supabase 端修正，因此 `useCharacterData.js` 於讀取時會自動修剪所有用於比對與查找的欄位（id、角色名），重新執行 `fetch-data` 也不會受影響。

*部分功能與資料 fork 自 beymetchannel/PlakoroBattle，特此感謝 beymetchannel 開源
